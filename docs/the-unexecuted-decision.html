The money stops moving when the argument ends

When a Polymarket market resolves, the uncertainty is gone. The oracle has reported, the payout ratios are fixed on chain, and every outcome token has a known value: one pUSD for the winning side, zero for the other. And yet nothing moves. The collateral sits inside the Conditional Tokens contract until somebody sends a transaction that says, in effect, yes, I would like the thing I already won.

This is a strange category of work. Not a trade, because there is no counterparty and no price. Not a race, because there is no deadline: winning tokens stay redeemable forever. It is a chore, and chores get forgotten, which is why Polymarket runs an AutoRedeemer of its own. In a four thousand block sample it was the busiest redeemer on Polygon, with 19,914 redemptions. But it redeems for wallets Polymarket operates. A position held by an agent's treasury, a Safe, or a market maker's own wallet is not covered, and stays unredeemed until a person remembers.

A settled decision, a known amount, a call anyone can make, and nobody making it. That is a good shape for automation and an awkward one for an agent, because the agent is the least trustworthy participant in the transaction.

payoutDenominator is zero until the oracle reports and non-zero forever after, which makes it the narrowest on-chain fact meaning this market is settled. Everything the redeem call needs is fixed text, above, in the file the reviewer reads.

The dry run covers the exact call that later executes, because there is no later interpretation for it to miss.

KeeperHub's simulator makes the cost of the alternative concrete: it skips any node whose network, address, ABI, function or arguments contain a template, because it cannot know what those resolve to until upstream steps run. A templated workflow reviews as a shape and dry runs as nothing. A SHA-256 over the canonical workflow is recorded at authoring time; deployment refuses a plan whose hash changed after review, and the dry run re-reads the deployed workflow and compares hashes again. The claim is a check, not a promise.

One address that looked authoritative and was wrong

No contract address or signature in this build was used on the strength of documentation alone. That rule earned its keep immediately.

Polymarket's docs give the standard collateral adapter as 0xAdA100Db…FcE1f. The README of Polymarket's own ctf-exchange-v2 repository gives 0xADa10087…09718. Both are real, deployed, plausible contracts, and bytecode presence cannot separate them. Live behaviour can.

The repository README was last edited in April. An integration built from the more official looking source would have pointed at a deployment the world has moved off.

The last row matters more than it looks. A trigger that fires twice is a double spend in most designs. Here the framework skips any outcome where the caller's balance is zero and only transfers when the payout exceeds zero, and the collateral wrapper has no zero-amount guard. A second run moves nothing rather than reverting. Idempotency is a property of the contracts, confirmed by reading them, not a lock bolted on afterwards.

What the platform could not do, and what is still unproven

The honest version of this workflow triggers on ConditionResolution, the settlement event itself. It does not, because KeeperHub's event trigger cannot filter on event arguments: its tracker reads a network, a contract, an ABI and an event name, and nothing else. Polymarket resolves roughly seven hundred markets an hour, so watching one market that way would wake the workflow for all of them and bill an execution each time, about 9,500 runs a day to catch one redemption.

So the default polls, which is the cheaper of two imperfect options and costs only latency, since redemption has no deadline. The event version is implemented anyway, carrying its cost warning in the code, for when filtering lands. KeeperHub's own issue tracker describes the better answer, a trigger that evaluates a contract read once per block; its evaluation core merged on 11 September but is not yet exposed through the public schema, the API or the builder.

And the part a reader should keep in front of them: no value has moved yet. The contract checks pass, the tests pass, the workflow authors and hashes and writes itself to a reviewable file, and none of that is a transaction. Execution needs an organization key and a funded wallet. Until then the audit trail reports zero runs rather than a sample row. The neg-risk adapter path is implemented and has never run against a neg-risk market, which is an untested branch inside the headline feature. One workflow watches one market, so a portfolio means a workflow per position.

The interesting claim is not that a redemption can be automated. It is that the part which knows about the outside world and the part which spends money can be kept separate enough that a person can read the second one in full before it runs.
